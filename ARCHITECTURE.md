# Hermes 跨设备自增长知识库完整工程架构方案

> 一句话：面向多设备（macOS / Linux / 云端主机）与多 Agent 协同的自增长、自愈型 Markdown 知识库系统工程架构方案。

---

## 一、 设计哲学与第一性原理

传统的单体 Agent 记忆或初级 RAG 系统在运行 1~3 个月后，几乎必然走向系统崩溃，根源在于无法解决大模型记忆的 **四大根本死穴**：

1. **垃圾进垃圾出（GIGO）**：把几万条原始对话、调试报错、随口调侃直接喂给向量库，检索召回的全是噪声；
2. **知识腐烂与时空颠倒**：模型把历史笔记里“当时的配置与报错”当成“当前的系统现状”，产生高危幻觉；
3. **上下文膨胀与成本失控**：让 Agent 带着几十万字的原始记录边思考边改文件，单字消耗冲到 600 Token；
4. **并发互斥破坏（熵增灾难）**：多个设备或多个子 Agent 同时读写 Markdown，导致格式损坏、正文被抹除、关键技术细节丢失。

为了根治以上问题，本方案确立三大底层工程原则：
- **三层物理漏斗原则**：严格隔离“不可变历史语料（Raw）”、“毫秒级检索坐标（Index）”与“结构化活知识（Wiki）”；
- **时空彻底解耦原则**：静态经验沉淀进 Wiki，动态现状由现场实测探针直出，Wiki 绝不充当监控台；
- **外硬内软原则**：所有流程流转、互斥写入、反引号代码保留率必须由外部脚本做 **Fail-Closed 硬门禁**，大模型只作为纯推理肌肉。

## 二、 全局系统架构拓扑

整套系统采用模块化分层设计，解耦数据摄取、模型提炼、物理落盘与无感召回：

```
+-----------------------------------------------------------------------------------+
|                              多端输入源 (Data Sources)                            |
|    多端开发机 (Claude Code / Codex 等)  |  宿主机/网关 (Hermes Agent)  |  多端扩展输入 |
+-----------------------------------------------------------------------------------+
                                          |
                                          | [每晚 03:00 / 实时归集拉取]
                                          v
+-----------------------------------------------------------------------------------+
|                        【第 1 层：物理语料层】 raw/conversations/                  |
|  - 纯追加 (Append-Only)、只读物理源头                                              |
|  - 每一问一答打上全局唯一段 ID (格式: ^[kb:来源:片段id])                            |
+-----------------------------------------------------------------------------------+
                                          |
                                          | [本地分块 + 向量/全文索引]
                                          v
+-----------------------------------------------------------------------------------+
|                        【第 2 层：切片坐标系】 kb.sqlite + QMD                     |
|  - SQLite 保存 chunk 切片与元数据                                                 |
|  - QMD (BM25 + 本地向量混合检索) 提供毫秒级主题空间寻址                            |
+-----------------------------------------------------------------------------------+
                                          |
                                          | [两步流水线：单次纯推理 ➔ 排他写锁并入]
                                          v
+-----------------------------------------------------------------------------------+
|                     【第 3 层：可自愈 Markdown Wiki】 ~/brain/wiki/                |
|  projects/ (项目)  |  entities/ (实体)  |  concepts/ (方法论)  |  _meta/map.md    |
|  - Karpathy LLM-Wiki 规范、双向链互通、事实死挂出处、单页 < 400 行                  |
+-----------------------------------------------------------------------------------+
                                          ^
                                          | [kb-recall 插件动态拦截与注入]
                                          |
+-----------------------------------------------------------------------------------+
|                            运行时消费层 (Runtime Context)                         |
|  - 问即时状态 ➔ 探针截胡直接读取 now.md (零模型推理、零历史污染)                   |
|  - 问业务经验 ➔ QMD 命中最相关 3~4 个 Wiki 摘要动态注入 System Prompt (聊完即焚)     |
+-----------------------------------------------------------------------------------+
```

## 三、 核心流转流水线与流程图

### 1. 每日夜间数据摄取与入库流水线（Ingestion Pipeline）

每天凌晨固定触发，将全端产生的新会话增量消化并建立坐标索引：

```
[定时触发 03:00]
       |
       v
+---------------------+
| 1. rsync / SCP 同步 | <--- 从 Mac 等另一台机器同步当天的 session JSONL 到 MAC_SYNC_DIR
+---------------------+
       |
       v
+---------------------+
| 2. kb build (切片)  | <--- 解析会话角色，切分成问答对 chunk，写入 kb.sqlite
+---------------------+
       |
       v
+---------------------+
| 3. QMD 索引刷新     | <--- 增量更新 QMD 向量库与 BM25 词表，生成语义坐标
+---------------------+
       |
       v
+---------------------+
| 4. 唤醒提炼流水线   | <--- 生成 pending 批次，交由两步入库法处理
+---------------------+
```

---

### 2. 两步入库流水线（Two-Stage Distillation Pipeline）

解决“Agent 边读材料边调工具导致 Token 成本暴增”以及“并发写坏文件”的关键机制：

```
+-----------------------------------------------------------------------------+
| 第一步：低成本无工具提炼 (Extract)                                          |
|                                                                             |
|  [未读对话批次 (100~200 段)]                                                 |
|            |                                                                |
|            v                                                                |
|  [轻量极速模型 (无工具调用)]  <--- 仅做纯文本结构化蒸馏                      |
|            |                                                                |
|            v                                                                |
|  [结构化 JSON 知识点清单]                                                   |
|    - 新知识 (New Fact)                                                      |
|    - 更新 (Update)                                                          |
|    - 纠错 (Correction)                                                      |
|    - 强标事实出处 basis (user / output / agent观点标"未核实")               |
+-----------------------------------------------------------------------------+
                                     |
                                     | 产出中间态 JSON，放入待并入队列
                                     v
+-----------------------------------------------------------------------------+
| 第二步：排他写锁受控并入 (Merge)                                            |
|                                                                             |
|  [调度 Agent 唤醒]                                                          |
|            |                                                                |
|            v                                                                |
|  [竞争 kb_lock 排他文件锁] <--- 拿不到锁则优雅休眠等待，彻底杜绝并发冲突     |
|            |                                                                |
|            v                                                                |
|  [QMD 寻址定位归宿页面]    <--- 毫秒级命中 projects/ 或 entities/ 目标文件   |
|            |                                                                |
|            v                                                                |
|  [原子化 Patch 修改目标页]  <--- 严禁整页重写，只用 patch 增量注入           |
|            |                                                                |
|            v                                                                |
|  [释放 kb_lock 文件锁]     <--- 提交修改，释放锁供下一任务使用               |
+-----------------------------------------------------------------------------+
```

### 3. 反熵增自愈与收敛机制（Consolidation Pipeline）

知识库随时间推移必定会产生碎片页和过度膨胀的大页。系统内置自愈调度：

```
[扫描 Wiki 全库]
       |
       +---------------------------------------+
       |                                       |
       v                                       v
【分支 A：碎片页合并】                   【分支 B：膨胀大页重整】
(检测到相同前缀的多个细碎页面)           (单页超过 400 行或 40KB)
       |                                       |
       v                                       v
调用 Agent 将零散做法并入主页           强制按标准结构四段式重整：
(如将排障碎页合入对应项目页)             1. 现状 (只留真实有效事实)
       |                                 2. 做法与排障 (小标题归并)
       |                                 3. 规则和重要决定 (仍然生效)
       |                                 4. 历史 (旧快照浓缩为一两行)
       |                                       |
       +-------------------+-------------------+
                           |
                           v
              +-------------------------+
              | 提交前跑 --check 门禁   |
              +-------------------------+
                           |
            +--------------+--------------+
            |                             |
       [校验通过]                    [校验拒绝]
            |                             |
            v                             v
  执行 --done 正式提交入库          物理打回重写：
  全库超链接由脚本自动改写指向      - 反引号代码保留率 < 70%
                                    - 出处成串堆砌未死挂正文
```

```

                                 v

                                 |

```

## 四、 核心防护门禁（Fail-Closed 规则集）

1. **反引号具体技术项 70% 硬门禁**：
   - 大模型在合并与重整 Markdown 时，天生具有“过度概括”的倾向，容易将具体的端口、命令、环境变量抹除为一两句空洞描述。
   - `wiki_consolidate.py` 在执行 `--done` 验收时，会用正则提取重构前后反引号里的具体项（命令、路径、端口、版本、配置项）逐一比对（一行堆一串的清单行不计入）；**保留率低于 70% 拦截，禁止交卷**。
2. **出处强行死绑（Traceability Gate）**：
   - 严禁在文末堆砌一大串出处清单。
   - 每一条沉淀出来的规则、参数、结论，必须紧跟出处引用 `^[kb:来源:片段id]`。无证据断言直接判定为不合规。
3. **单一模型端点与就绪让路**（10-10 起）：
   - 提炼只调用一个 OpenAI 兼容端点（`KB_MODEL` + `OPENAI_BASE_URL` + `OPENAI_API_KEY`，例如 Gemini 中转），统一经 `scripts/kb_llm.py`；
   - `kb_models.pick()` 在端点没配好时返回「未就绪」，提炼 / 并入任务直接让路、不叫醒模型；模型输出解析失败会重试，仍失败则本批不标记、下次自动减半批次；
   - 旧的 Grok / luna 额度分路保留为可选（`KB_LEGACY_ROUTING=1`），默认关闭。
4. **配置集中与去个人化**：
   - 所有路径、项目根目录、同步主机、MCP 地址都由 `scripts/kb_config.py` 统一读取（环境变量 > `~/.config/hermes-kb/config.toml` > 默认值），密钥只从环境变量或 `~/.hermes/.env` 读取；
   - 新会话使用更长的会话 ID，已收录会话沿用旧 ID，既有出处 `^[kb:...]` 不失效。

## 五、 跨设备落地复现指南（Mac/Linux 极简部署）

将本套架构复制到一台全新机器（如你的个人 Mac 笔记本）的最小执行路径：

### 1. 软件环境与依赖准备
- **基础运行库**：Python 3.10+，安装 `requests` 等基础库；
- **安装 QMD 本地检索器**：
  ```bash
  # 安装 qmd 并建立本地两层索引空间
  qmd collection add wiki ~/brain/wiki
  qmd collection add raw ~/brain/raw/conversations
  ```

### 2. 核心文件与资产落地结构
```
~/brain/
  ├── raw/conversations/    # 原始对话层 (只读不可变)
  ├── kb/
  │   ├── kb.sqlite         # 切片数据库
  │   └── now.md            # 每 15 分钟生成的即时现状看板
  └── wiki/                 # 结构化知识库
      ├── projects/         # 项目级事实
      ├── entities/         # 实体、机器、服务与账号
      ├── concepts/         # 方法论、SOP 与通用规程
      ├── _meta/map.md      # 全局雷达索引地图 (<=30行)
      └── log.md            # 全量更新流水账
```

### 3. 核心脚本移植（放置于 `~/.hermes/scripts/`）
- `wiki_extract.py`：低成本纯文本无工具提炼脚本；
- `wiki_merge_feed.py`：排他写锁受控入库脚本；
- `wiki_consolidate.py`：防膨胀页面合并重整门禁脚本；
- `kb_lock.py`：基于文件锁与超时的单写入并发控制器。

### 4. 接入定时调度（Hermes Cron 或系统 Crontab）
- `0 3 * * *`：执行夜间多端会话拉取与 `kb build`；
- `*/30 * * * *`：执行 `wiki_extract.py` 消化待办；
- `*/10 * * * *`：执行 `wiki_merge_feed.py` 语义并入；
- 结合 `kb-recall` 插件，将 QMD 检索能力无感注入日常交互，实现知识库的真正自治自增长。
